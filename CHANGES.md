# Changes

Этот файл кратко показывает, как изменилось исходное тестовое задание.

## Что было изначально

Изначально проект был простым CRUD API для обычных задач.

Было реализовано:

- сущность `Task`
- таблица `tasks`
- HTTP API для создания, чтения, обновления и удаления задач
- Swagger/OpenAPI
- базовая слоистая структура: `domain -> usecase -> repository -> transport`

Не было:

- периодических задач
- шаблонов задач
- генерации задач по расписанию
- фонового sync
- календарной логики повторений

## Что изменено

### 1. Добавлены recurring task templates

Появилась отдельная сущность шаблона, которая хранит:

- `title`
- `description`
- `timezone`
- `start_date`
- `end_date`
- `recurrence_type`
- `recurrence_settings`
- `is_active`

### 2. Добавлены типы периодичности

Реализованы:

- `daily`
- `monthly`
- `specific_dates`
- `even_odd`
- `weekdays`

### 3. Добавлена генерация task instances

По шаблону автоматически создаются обычные задачи.

Для generated tasks добавлены поля:

- `template_id`
- `scheduled_for`

При этом `scheduled_for` не обязателен для ручной задачи.

### 4. Добавлен новый API для шаблонов

Добавлены endpoint'ы:

- `POST /api/v1/task-templates`
- `GET /api/v1/task-templates`
- `GET /api/v1/task-templates/{id}`
- `PUT /api/v1/task-templates/{id}`
- `DELETE /api/v1/task-templates/{id}`

### 5. Добавлен фоновый sync

Сервис теперь периодически проходит по активным шаблонам и догенерирует недостающие задачи.

## Какие проблемы были исправлены

### 1. Неатомарный create/update шаблона

Изначально шаблон и generated tasks могли измениться частично.

Исправление:

- создание шаблона и первичная генерация выполняются в транзакции
- update шаблона, удаление будущих задач и регенерация тоже выполняются в транзакции

### 2. Потеря текущей работы при update шаблона

Раньше можно было потерять уже актуальные экземпляры задач.

Исправление:

- при update удаляются только будущие экземпляры
- и только в статусе `new`

### 3. Слишком мягкий JSON decoding

Раньше handler принимал trailing payload после первого JSON.

Исправление:

- request body теперь должен содержать ровно один JSON-объект

### 4. Ошибка одного шаблона останавливала весь background sync

Раньше один проблемный шаблон останавливал обработку остальных.

Исправление:

- ошибка по одному шаблону собирается в aggregate error
- остальные шаблоны продолжают обрабатываться

### 5. Delete шаблона не очищал уже нагенерённые будущие задачи

Раньше deactivation только выключал дальнейшую генерацию.

Исправление:

При `DELETE /api/v1/task-templates/{id}`:

- шаблон деактивируется
- будущие generated task instances в статусе `new` удаляются
- прошлые, текущие и уже начатые/завершённые экземпляры остаются

## Как эволюционировало решение

Проект прошёл путь:

1. от простого CRUD для задач
2. к модели `task instance + recurring task template`
3. затем к безопасной транзакционной генерации
4. затем к более строгому API-контракту и документации
5. затем к более устойчивому фоновому sync и корректной delete semantics

## Что ещё можно улучшить

Если развивать проект дальше, логичные следующие шаги:

- добавить DB-level constraints (`CHECK`, `FOREIGN KEY`)
- написать integration tests с PostgreSQL
- добавить фильтрацию и пагинацию для `/tasks`
- улучшить наблюдаемость фонового sync

## Итог

В результате тестовое задание превратилось из простого CRUD-сервиса в backend, который умеет:

- хранить обычные задачи
- хранить шаблоны периодических задач
- автоматически генерировать задачи
- безопасно обновлять шаблоны через транзакции
- корректно деактивировать шаблоны без потери истории и текущей работы
